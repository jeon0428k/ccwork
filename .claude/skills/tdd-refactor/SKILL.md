# TDD Refactor

`tdd-green`으로 테스트가 전부 통과하는 상태를 입력으로, **동작(테스트 결과)을 바꾸지 않고 코드 구조만 개선**한다.
TDD 사이클의 Refactor — 매 변경마다 테스트로 회귀를 확인하며, 깨지면 즉시 롤백한다.

- **입력**: 이슈 번호 `$ARGUMENTS` (예: `/tdd-refactor 6`).
- **대상**: 이번 이슈에서 변경된 `src/` 파일(테스트 파일 제외)만.
- **도구**: Vitest (`npm test` = `vitest run`), `git diff main...HEAD`.

## Workflow

### 1. 컨벤션 파악

`CLAUDE.md`를 읽어 프로젝트 컨벤션(네이밍, 컴포넌트/상태 패턴, 스타일링 규칙)을 파악한다. 리팩터링 방향의 기준이 된다.

### 2. 시작 상태 = 전체 통과 확인

```bash
npm test
```

Refactor는 **전부 초록**에서 시작한다. 실패가 있으면 멈추고 개발자에게 보고(아직 Green 단계가 안 끝남).

### 3. 리팩터링 대상 식별

```bash
git diff main...HEAD --name-only -- src/
```

- 이번 이슈에서 변경된 `src/` 파일 목록을 추출한다.
- **테스트 파일(`*.test.ts` / `*.test.tsx`)은 제외**한다.
- 남은 파일을 아래 **범용 점검 기준**으로 검토한다.
  - **중복 제거** — 같은 로직이 반복되는가.
  - **네이밍 명확성** — 의도를 드러내는 이름인가.
  - **단일 책임** — 하나의 함수/컴포넌트가 너무 많은 일을 하는가.
  - **불필요한 복잡도** — 매직 넘버, 과도한 중첩, 불필요한 추상화가 있는가.
  - **CLAUDE.md 컨벤션 불일치** — 프로젝트 패턴과 어긋나는 코드가 있는가.

### 4. 대상 목록 보고 → 승인 대기 〈게이트〉

발견한 리팩터링 항목을 `파일:라인` + 근거와 함께 목록으로 보고하고 **개발자 승인을 기다린다.** 승인 전에는 코드를 고치지 않는다.

### 5. 한 번에 하나씩 변경 → 테스트

승인된 항목을 **하나씩** 적용한다. 변경 1건마다:

```bash
npm test
```

통과를 확인한 뒤 다음 항목으로 넘어간다.

### 6. 깨지면 즉시 롤백

테스트가 실패하면 그 변경을 **즉시 되돌리고**(원복) 다른 접근을 시도한다. 깨진 채로 다음으로 넘어가지 않는다.

### 7. 변경 요약

리팩터링 전후를 항목별로 요약한다(무엇을·왜 바꿨는지, 영향 파일, 테스트 결과).

## Guidelines / Constraints

- **새 기능 추가 금지** — 동작은 그대로, 구조만 개선한다.
- **테스트 파일 수정 금지** — `*.test.ts` / `*.test.tsx`는 건드리지 않는다(테스트가 동작의 기준).
- **`src/` 디렉터리 밖 수정 금지.**
- **대상 파일 범위(§3 `git diff` 결과) 밖 수정 금지** — 이번 이슈와 무관한 파일은 손대지 않는다.
- **승인 게이트 준수** — §4 승인 전 코드 변경 금지.
- 입력은 이슈 번호(`$ARGUMENTS`).

## Output

- 구조가 개선된 `src/` 코드 — 동작 변화 없음.
- 각 변경마다 `npm test` 통과(회귀 0) 확인.
- 리팩터링 전후 변경 요약(항목·근거·영향 파일).
- 다음 단계: PR/머지 또는 다음 이슈.
