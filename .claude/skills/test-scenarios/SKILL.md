# Test Scenarios

GitHub 이슈 한 건을 입력받아 **시그니처 확정 → 테스트 시나리오 도출**을 순서대로 처리한다.
TDD의 "Red" 직전 단계 — 무엇을 어떤 형태로 만들지(시그니처)와 무엇을 검증할지(시나리오)를
확정하되, **구현 코드도 테스트 코드도 쓰지 않는다.**

- **입력**: GitHub 이슈 번호 `$ARGUMENTS` (예: `/test-scenarios 6`).
- **산출물**: `docs/features/tag/issue-{N}.md` (상단=시그니처, 하단=시나리오).
- **실행 컨텍스트**: 서브에이전트 **fork**로 실행한다(메인 대화 컨텍스트를 상속하되 격리).

> **승인 게이트가 2곳 있다.** 시그니처 확정 후(2단계)와 시나리오 도출 후(7단계).
> 게이트마다 멈추고 개발자 승인을 받은 뒤 다음으로 넘어간다.

## Workflow

### 1. 시그니처 확정 (구현 금지)

입력: `gh issue view {N}` 내용 + `docs/features/tag/prd.md` + 코드베이스.
다음을 확정한다 — **구현 코드는 절대 작성하지 않는다.**

- **함수 시그니처**: 이름, 파라미터 타입, 반환 타입.
- **에러 케이스**: 어떤 상황에서 무엇을 throw 하는지(또는 조용히 무시하는지).
- **컴포넌트 Props 타입**: `interface ${Component}Props`.
- **기존 패턴 준수**: `src/api/notes.ts`(순수 fetch), `NotesContext`(상태/노출 함수 동사),
  컴포넌트 Props 패턴(`on`+PascalCase, `is`+PascalCase, named export)을 따른다.

### 2. 시그니처 검토 — `[GATE]`

확정한 시그니처를 개발자에게 **보여주고 승인**을 받는다. 승인 전 다음 단계로 가지 않는다.

### 3. 시그니처 기록

승인된 시그니처를 `docs/features/tag/issue-{N}.md` **상단**에 기록한다(파일 없으면 생성).

### 4. 테스트 시나리오 도출 (테스트 코드 금지)

확정 시그니처를 기반으로 시나리오를 도출한다. **테스트 코드는 작성하지 않는다.**

- 분류: **정상 / 경계 / 예외**.
- 형식: `[정상|경계|예외] 함수명 - should [기대동작] when [조건]`

### 5. 시나리오 기록

도출된 시나리오를 `docs/features/tag/issue-{N}.md` **하단**에 추가한다.

### 6. AC 대조 (커버리지 확인)

- `gh issue view {N}` 로 이슈의 **Acceptance Criteria** 목록을 읽는다.
- 시나리오가 없는 AC가 있으면 시나리오를 **추가**한다.
- **모든 AC가 최소 1개 이상의 시나리오로 커버**되는지 확인한다(누락 0건).

### 7. 시나리오 검토 — `[GATE]`

최종 시나리오 + AC 커버리지 표를 개발자에게 보여주고 **승인**을 받는다.

## Guidelines / Constraints

- **구현 코드·테스트 코드를 절대 작성하지 않는다.** 이 스킬의 산출물은 시그니처와 시나리오뿐.
- **2개의 `[GATE]`에서 반드시 멈춘다**(2단계 시그니처, 7단계 시나리오). 승인 없이 진행 금지.
- 시그니처는 코드베이스 **기존 패턴을 따른다**(새 관습을 발명하지 않는다).
- 모든 AC는 최소 1개 시나리오로 커버되어야 한다 — 누락 시 시나리오를 보강한다.
- 산출물 파일은 한 이슈당 하나(`issue-{N}.md`): 상단 시그니처, 하단 시나리오.

## Output

- `docs/features/tag/issue-{N}.md`
  - 상단: 확정 시그니처(함수/에러/Props)
  - 하단: 테스트 시나리오(정상/경계/예외) + AC 커버리지 대조표
- 다음 단계: 이 산출물을 입력으로 **TDD 구현**(Red→Green→Refactor).
