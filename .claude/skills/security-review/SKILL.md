# Security Review

TDD 사이클의 Refactor가 끝나고 **커밋하기 직전**, 타입 안정성과 보안을 점검한다.
스캔 결과를 자동으로 고치지 않고 **분류 후 보고**하며, 개발자가 승인한 "즉시 수정 필요" 항목만 처리한다.

- **입력**: 이슈 번호 `$ARGUMENTS` (예: `/security-review 6`).
- **도구**: `tsc`, `npm audit`, `grep`.

## Workflow

### 1. 타입 오류 수집

```bash
npx tsc --noEmit
```

빌드 실패 수준의 타입 오류를 모은다(파일·라인·메시지).

### 2. 의존성 취약점 수집

```bash
npm audit
```

심각도(critical/high/moderate/low)와 패키지·경로를 모은다.

### 3. 환경변수 노출 확인

`.env` 변수가 `src/` 코드에서 직접 노출되는지 grep으로 확인한다.

```bash
grep -rnE "VITE_|process\.env|import\.meta\.env" src/
```

`.env`의 키 이름과 대조해, 비밀값이 클라이언트 번들에 직접 박히는 패턴이 있는지 본다.

### 4. 결과 3단계 분류 → 보고 〈게이트〉

수집 결과를 다음 3가지로 분류해 개발자에게 보고하고 **승인을 기다린다.**

- 🔴 **즉시 수정 필요** — 보안 위험 또는 빌드 실패 수준(타입 에러, high/critical 취약점, 비밀값 노출).
- 🟡 **권장 수정** — 코드 품질 저하(moderate 이하 취약점, 경미한 타입 우회 등).
- ⚪ **무시 가능** — false positive 또는 의도된 패턴(근거 명시).

### 5. 승인 후 "즉시 수정 필요"만 처리

개발자 승인을 받은 뒤 **🔴 항목만** 수정한다. 🟡·⚪는 보고로만 남기고 손대지 않는다.

### 6. 재스캔 → 클린 확인

수정 후 1~3단계를 다시 돌려 🔴 항목이 해소된 **클린 상태**를 확인한다.

## Guidelines / Constraints

- **판단이 필요한 항목은 반드시 개발자 승인 후 수정** — §4 승인 전 코드 변경 금지.
- **테스트 파일 수정 금지** — `*.test.ts` / `*.test.tsx`는 건드리지 않는다.
- **`npm audit fix --force` 사용 금지** — 호환성 깨짐 위험. 필요 시 개별 패키지 수동 조정.
- 🟡·⚪로 분류한 항목은 임의로 수정하지 않는다(보고만).
- 입력은 이슈 번호(`$ARGUMENTS`).

## Output

- 타입·취약점·env 노출 스캔 결과를 🔴/🟡/⚪로 분류한 보고서.
- 승인된 🔴 항목 수정 + 재스캔 클린 확인 결과.
- 다음 단계: 커밋/PR.
