# TDD Loop (오케스트레이션 컨테이너)

이슈 1개(`$ARGUMENTS` = GitHub 이슈 번호)에 대해 TDD 풀 사이클 7단계를 **순서대로** 실행한다.
각 단계는 **기존 스킬/에이전트를 그대로 호출**하며, 그 내부의 승인 게이트는 살아 있다.
이 컨테이너는 **순서만 보장**하고 단계 사이에 진행 메시지만 출력한다 — 자체적으로
"다음 단계 진행할까요?" 같은 추가 게이트를 만들지 않는다.

> 입력: `$ARGUMENTS` = 이슈 번호 (예: `/tdd-cycle 20`). 비어 있으면 이슈 번호를 먼저 요청한다.

## Workflow

### 0. 사전 점검 (컨테이너가 직접 수행)

순서대로 확인하고, **하나라도 실패하면 어디서 멈췄는지 출력하고 중단**한다.

- `gh issue view $ARGUMENTS` — 이슈 본문 + Acceptance Criteria 확인(요약 출력).
- `git status` — **uncommitted 변경이 있으면 중단**(안전 차원).
- 최신 `dev` 확보: `dev` 체크아웃 → `git pull`로 머지분 반영(작업 브랜치는 최신 `dev`에서 분기).
- 작업 브랜치(`feat/<issue-slug>`) 존재 여부 분기:
  - **이미 있으면** → 동일 이슈 재실행으로 간주하고 **사용자에게 확인**(덮어쓸지 / 취소할지). 응답 전까지 진행하지 않는다.
  - **없으면** → `dev`에서 `feat/<issue-slug>` 분기 + 체크아웃.
- 위 단계 중 하나라도 실패하면 사용자에게 알리고 중단한다.

사전 점검 통과 후 진행 메시지를 출력하고 1단계로 넘어간다.

### 1. `/test-scenarios $ARGUMENTS`

- 시그니처 + 시나리오(정상/경계/예외) 도출.
- **시그니처 승인 게이트 → 시나리오 승인 게이트** (하위 스킬 내부 게이트 그대로 유지).

### 2. `/tdd-red $ARGUMENTS`

- 승인된 시나리오 → 실패 테스트로 변환, 즉시 실행해 실패 확인.
- 테스트 collect 실패 시 stub 생성 안내(하위 스킬 처리).

### 3. `/tdd-green $ARGUMENTS`

- 실패 테스트를 통과시키는 최소 구현, 회귀 감시.
- 피드백 루프(최대 5회)는 하위 스킬 규칙을 따른다.

### 4. `@ac-verifier $ARGUMENTS`

- 이슈의 AC 충족 여부를 독립 검증(테스트 통과 ≠ AC 충족).
- **갭이 있으면 사용자에게 보고**하고, 그 처리(추가 작업/진행)는 사용자 판단을 따른다.

### 5. `/tdd-refactor $ARGUMENTS`

- 테스트 통과를 유지하며 구조 개선. **변경마다 `npm test`**로 회귀 방지(하위 스킬 규칙).

### 6. `/security-review $ARGUMENTS`

- `tsc` / `npm audit` / 환경변수·보안 패턴 점검.
- "즉시 수정 / 권장 수정 / 무시 가능" 등급별 처리 안내(하위 스킬 게이트 유지).

### 7. `/create-pr`

- 커밋 메시지 commitlint 통과 확인.
- **PR base = `dev`** (프로젝트 통합 브랜치).
- PR body에 **`Closes #$ARGUMENTS`** 포함.
- 생성 후 **이슈에 PR 링크 코멘트**(`gh issue comment`).

## Guidelines / Constraints

- **컨테이너는 순서만 보장한다.** 각 단계 호출 사이에 "▶ N단계: … 시작" 류의 진행 메시지만 출력한다.
- **하위 스킬/에이전트의 승인 게이트는 그대로 작동한다** — 사용자가 응답해야 다음으로 진행한다.
- **컨테이너 자체는 추가 게이트("다음 단계 진행할까요?")를 만들지 않는다.** 한 단계가 (게이트 통과 포함) 끝나면 곧바로 다음 단계를 호출한다.
- **단계 실패 시**: 어느 단계에서 왜 멈췄는지 명확히 출력하고 **즉시 중단**한다(다음 단계로 넘어가지 않는다).
- 분기/PR base는 **`dev` 기준**이다(CLAUDE.md의 TDD 이슈 사이클 워크플로우 — 작업 브랜치는 최신 `dev`에서 분기, PR은 `dev`를 base로).

## Output

- 각 단계의 산출물은 해당 하위 스킬이 만든다(시나리오 문서, 실패 테스트, 구현, 리팩터, 점검 보고, PR).
- 최종 산출물: `feature/<spec>`를 base로 한 PR(본문에 `Closes #$ARGUMENTS`) + 이슈의 PR 링크 코멘트.
- 중단 시: 멈춘 단계 번호 + 사유를 출력.
